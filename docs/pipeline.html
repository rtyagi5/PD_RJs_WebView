01

What crosses the boundary

The engine is a web page inside someone else's app. Only three things cross in or out: a token on the way in, a stream of small messages on the way out, and one upload at the end. No pixel and no joint coordinate ever leaves the device.

02

Before the first frame: where the template comes from

The engine matches the patient against a 60-frame reference. That reference has to exist before the camera starts, so it is built at import time from a declarative config — not recorded from anyone.

Worth saying out loud when you present this. All 16 exercises currently run on the synthetic template. Their phase boundaries were authored by hand, not measured from anyone performing the movement.
03

The frame loop

This runs 30–60 times a second. The one structural surprise: drawing and inference are deliberately decoupled. The loop never waits for the pose model — it draws with the most recent result that finished, so a slow phone loses accuracy, not smoothness.

04

Inside the rep counter

A rep is not "the angle passed a threshold". It is a small state machine with five separate gates, each added in response to a real false count. This is where most of the engineering judgement in the codebase lives.

05

Which cue the patient actually hears

Only one message can be on screen at a time, so _pickFeedback() is a ladder: the first rung that matches wins and the rest never run. Where a cue sits on this ladder decides whether it is ever heard.

06

Code that looks live but isn't

Roughly two thousand lines never execute. Anyone reading the repo cold will find them and assume they matter — worth pointing at directly.
